# Bridge protocol (version 1, with v1.1 clarifications in Appendix A and the reset addendum)

Contract between the TypeScript extension (`BridgeClient`) and the Python bridge (`bridge/mpy_bridge.py`), plus the rules the bridge's internals must obey. Everything in `bridge/`, `tools/fakeboard.py` and `tests/` is built against this file; change it first, then the code, and note the change in `plan.md`. Decisions referenced: D-02, D-03, D-07, D-11, D-15; requirements: R-ARCH-*, RQ-SAFE-*, RQ-ID-*, RQ-RUN-*, RQ-CLOUD-*, RQ-GEN-*.

## 1. Process model

- The extension spawns **one bridge per VS Code window**, lazily, as an argv array (no shell): `python -I -u -X utf8 -X pycache_prefix=<writable dir> <ext>/bridge/mpy_bridge.py` with `windowsHide: true`, cwd = a neutral directory (never the workspace). The bridge inserts `bridge/vendor/` at `sys.path[0]` itself.
- **Protocol channel = the original stdout, UTF-8, `\n`-terminated, one JSON object per line.** At startup the bridge duplicates fd 1 for protocol use and redirects fd 1 to stderr (`os.dup`/`os.dup2`) so library `print()` can never corrupt the stream. Requests arrive on stdin, same framing.
- **stderr = human log lines** (`[level] message`), never parsed by the extension except for display in the log channel.
- **stdin EOF = quit.** On EOF the bridge (a) if a user program is running, interrupts it (Ctrl-C twice, best effort within 1 s; `RQ-SAFE-4`), (b) closes the port with the same close sequence as `disconnect`, (c) exits 0. A crashed parent therefore never leaves a COM port held or motors running.
- Exit codes: 0 clean; 2 fatal startup error (message on stderr and a final `{"ev":"fatal",...}` line if the channel is up); 3 unrecoverable internal error.
- The first line the bridge writes is the `hello` event.

## 2. Framing

```
request  : {"id": <int>, "op": "<name>", ...args}
response : {"id": <int>, "ok": true, ...result}
         | {"id": <int>, "ok": false, "error": {"code": "E_...", "message": "<english, user-readable>", "detail": "<raw cause>", "hint": "<what to do next>"}}
event    : {"ev": "<name>", ...fields}          (no id)
```

- Binary data is base64 in a field named `b64`. Text is UTF-8. Lines are limited to 4 MiB; file contents are never carried in the JSON (the bridge reads/writes local files itself, given absolute local paths), only console bytes.
- Requests are processed by the **port-owner worker** in priority order (section 6). A request's response is sent when it completes; long operations send `progress` events first. `id` values are chosen by the client; a response always echoes the id; unknown ops get `E_UNSUPPORTED`.
- **Local paths** (`local` fields) are absolute, as given by the OS (backslashes on Windows are fine), and may contain spaces, parentheses, `@` and non-ASCII (`RQ-CLOUD-1`). **Device paths** (`remote`, `path`, `src`, `dst`) are POSIX, absolute, `/`-separated.
- `hello`: `{"ev":"hello","proto":1,"bridge":"<version>","python":"3.x.y","pyserial":"3.5","platform":"darwin|win32|linux","pid":<int>,"vendored":{"mpremote":"1.29.0"|null}}`.

All ops are idempotent unless stated. "Queue class" is the priority class from section 6.

### Error codes (`error.code`) and what the client does

`E_PORT_BUSY` (another program holds it: show the "close Thonny/Arduino/PlatformIO/other VS Code window" checklist + Retry; **stop auto-reconnect**), `E_NO_DEVICE` (port missing/unplugged), `E_PERMISSION` (Linux dialout / driver), `E_NOT_CONNECTED`, `E_ALREADY_CONNECTED`, `E_RAW_REPL_TIMEOUT` (could not enter raw REPL: a program ignoring Ctrl-C, or not MicroPython), `E_PROGRAM_RUNNING` (op needs an idle board; client asks or defers), `E_BOARD_RESET` (the board reset under us; client re-syncs), `E_BOARD_UNRESPONSIVE` (stop timed out), `E_FS_ERRNO` (device filesystem error; `detail` carries the errno name, `message` explains), `E_LOCAL_IO` (local file read/write failed), `E_SHADOWS_MODULE`, `E_UNSUPPORTED`, `E_CANCELLED`, `E_PROTOCOL` (bad request), `E_SAFE_MODE` (see section 8), `E_INTERNAL` (bug; `detail` has the traceback). Messages are English and say what to do next; classification must not depend on English substrings of serial output.

## 4. Events

| ev | fields | meaning |
|---|---|---|
| `hello` | see section 2 | first line |
| `state` | `state, prev, reason?, port?` | state machine transition (section 5); also emitted on unplug (`disconnected`) |
| `repl` | `b64` | bytes from the board while the REPL is attached and no bridge op owns the port |
| `out` | `b64` | stdout bytes of a running `run` (raw-REPL stream), unmodified, CRLF as received |
| `err` | `b64` | the exception/traceback text of a `run` (the raw-REPL stderr channel), emitted when the program ends; tracebacks refer to `name` (the local path) when `compile` was used |
| `progress` | `id, label, done, total` | long ops (bytes for put/get, files for manifest) |
| `log` | `level, msg` | bridge diagnostics for the log channel |
| `fatal` | `message` | followed by exit |

## 5. State machine

States: `disconnected` -> `connecting` -> `idle` (friendly REPL at a prompt) <-> `running` (user program executing: `main.py` seen at connect, or `run`) / `rawop` (a bridge-owned operation holds the raw REPL) -> `disconnected` (unplug, close) -> `connecting` (reconnect is the **client's** decision and is bounded).

| from | event | to | notes |
|---|---|---|---|
| disconnected | `connect` ok | idle or running | no reset; `running` if output arrives and no prompt within the listen window |
| idle | file op | rawop -> idle | enter raw REPL **without soft reset**, run, exit raw REPL, swallow banner to the next `>>> `; if the REPL is attached, restore it (prompt redrawn with `\r`) |
| idle | `run` | running -> idle | Ctrl-C, raw REPL **with soft reset** (default `reset:true`), raw-paste the program, stream, on end return to the friendly prompt |
| running | `stop` | idle | Ctrl-C x2; if no prompt in `timeoutMs`: reply `stopped:false`, state stays `running` |
| running | file op | (deferred) | `E_PROGRAM_RUNNING` unless the client passes `interrupt:true` (a file op interrupts the program; the client asks once) |
| any | serial error / unplug | disconnected | `state` event with `reason:"unplugged"` and the error class |
| any | stdin EOF | (exit) | section 1 |

**Run (D-07, RQ-RUN-1/2):** if `local` is given the bridge reads the file; the source is wrapped as `exec(compile(<source repr>, <name or local path>, "exec"), {"__name__": "__main__"})` when the board supports `compile` (`caps.compile`), otherwise the raw source is sent and tracebacks show `<stdin>`. The source is sent with **raw paste** (window-flow-controlled) when `caps.paste`, else chunked raw exec. While `stdin:true`, bytes arriving via `tty.write` are forwarded to the device as soon as received (the raw REPL passes them to the program's `sys.stdin`). `exit:"interrupted"` when the program ended by `KeyboardInterrupt`.

## 6. Queue and priorities

One **port-owner worker** executes operations in this order (higher first): (0) **bypass** ops (`ping`, `stop`, `tty.write`, `cancel`, `shutdown`) run on the reader thread and take only the write lock; (1) `connect`/`disconnect`/`repl.*`; (2) `run`/`reset.*`; (3) explicit file ops (`fs.*`, `identity`, `exec`, `introspect.modules`) in arrival order; (4) coalescible background ops (`fs.put` flagged `background:true` for auto-sync, coalesced by `remote` path, last write wins; `fs.list`/`fs.manifest` flagged `background:true`). A new higher-class op does not abort a running op except `stop`/`cancel`. A **pump thread** forwards serial bytes as `repl` events while the REPL is attached and the worker is not inside an op.

## 7. Open/close policy (RQ-SAFE-1, D-15; measured in hardware session 1)

`openPolicy:"auto"` selects from this table; the table is data, extendable per adapter.

| Platform | Adapter | Open | Close | Evidence |
|---|---|---|---|---|
| macOS, Linux | any | `serial.Serial(...)` **default** (pyserial asserts DTR and RTS together; do not pre-set them low) | clear RTS then DTR, then close | **[E] CP2102 + class board: 0/2 resets**; forcing DTR/RTS low before open (V2) and mpremote's CP210x sequence (V3) reset the chip 2/2 |
| Windows | CP210x | **unverified**: candidate = mpremote 1.29 `transport_serial.py:70-85` sequence | RTS then DTR | S-08 [U] |
| Windows | other | pyserial default | RTS then DTR | [U] |
| any | URL (`socket://`, `rfc2217://`, pty) | default; tolerate `ENOTTY`/unsupported modem-line ioctls | plain | fake boards |

Hard reset (`reset.hard`): DTR low, RTS high for ~100 ms, RTS low (esptool `HardReset` style) where the adapter has an auto-reset circuit; otherwise `E_UNSUPPORTED`. Native-USB boards: `machine.reset()` is **not** sent implicitly; hard reset there is `E_UNSUPPORTED` in v1.

## 8. Safe mode (agents, tests, CI)

If the environment variable `MPY_SAFE_MODE=1` is set, `connect` to anything that is not a pyserial URL or a pty created by the test harness is refused with `E_SAFE_MODE`, unless `MPY_REAL_PORT` equals the requested port **exactly** (never `auto`). All test runners and agent shells set `MPY_SAFE_MODE=1`. The extension never sets it. This is defence in depth for `CLAUDE.md` rule "never open a serial port in tests".

## 9. Device-side code rules (snippets sent via raw REPL)

- Must run on **any** MicroPython 1.20+ port including small ones (ESP8266, RP2, STM32): only `os`, `sys`, `gc`, `time`, `binascii`/`ubinascii`; `hashlib`/`uhashlib` optional with a `hash:"none"` fallback; no f-strings, no walrus, no `os.walk`; `os.ilistdir` iterative with small buffers (<= 512 bytes) and constant extra RAM.
- Output is JSON-ish lines prefixed with a unique sentinel (`@@`) so banner/boot noise cannot be mistaken for data; file names are transmitted via `repr` or hex when they contain non-ASCII or control characters.
- Every snippet is tested on the **real MicroPython VM** (unix port, L0) and on the fake board; none may import application packages (`shield`) or touch hardware.

## 10. Bridge CLI mode (Gate G1, hardware sessions)

`python bridge/mpy_bridge.py --cli <op> [key=value ...] [--port P]` runs one op (or `--script file.jsonl`) with the same code path as the NDJSON server and prints the response JSON. Honors `MPY_SAFE_MODE`. Used by the instructor for G1 and by tests. It never resets the board except `reset.hard confirmed=true`.

## Appendix A - v1.1 clarifications adopted from the built and tested modules (2026-10-12)

These were discovered while implementing `bridge/link.py`, `bridge/errors.py` and `bridge/devfs.py` (103 + 150 tests green on Python 3.9/3.15). They **supersede** the corresponding text above where they differ. The reset tiers are specified in `protocol-addendum-reset.md`.

### A.1 Safe mode (section 8), stricter than first written
- `MPY_SAFE_MODE` counts as on for any value except empty, `0`, `false`, `no`, `off`.
- Allowed targets when on: `loop://`, `socket://` or `rfc2217://` to a **loopback host** (`127.x`, `localhost`, `::1`) parsed with a real URL parser (open defect: the current check is a string prefix and is fooled by `socket://127.0.0.1@example.com:80` and `127.`-prefixed hostnames), ptys registered by the harness (path must match `/dev/ttysN` or `/dev/pts/N`; `bridge.link.allow_harness_pty(path)` in-process or `MPY_HARNESS_PTYS`, `os.pathsep`-separated, for a separate process), and exactly `MPY_REAL_PORT` (never `auto`). `spy://`, `alt://`, `hwgrep://`, `cp2110://` and non-loopback hosts are `E_SAFE_MODE` because they can resolve to real devices. The check runs before any open.
- `tools/hwkit/mpy_hwkit.py` must honour the same variables (open defect).

### A.2 Connect and open policy (sections 3, 7)
- `connect.openPolicy` values: `auto | default | win-cp210x | pty | url`; anything else is `E_PROTOCOL`. `auto` picks `url`, `pty` or `default`; `win-cp210x` is selectable by name only (constant `AUTO_SELECT_WIN_CP210X = False`) until S-08. `url` closes with a plain `close()` and no RTS/DTR writes; `pty` tolerates `ENOTTY`/`EINVAL` on modem lines. On macOS `/dev/tty.X` is normalised to `/dev/cu.X`.
- `connect` should pass the adapter's `[vid, pid]` from `ports.list` (Link `usb_ids`); without it `portInfo.canHardReset` is `null`. `portInfo` = `{port, requested, baud, kind: "device"|"pty"|"url", policy, platform, pyserial, vid, pid, adapter, exclusive: true, canHardReset: true|false|null}`. (The reset addendum supersedes the hard-reset allowlist with the capability model of its section 2.)
- Entering the raw REPL sends a bare Ctrl-C (no leading CR), then waits up to `min(1 s, timeout/2)` for the interrupted program to return a prompt before Ctrl-A. Raw paste is requested per command when supported; once-per-session probing only decides whether to keep trying (an `R\x00` reply or the old-firmware banner selects chunked exec: 256 bytes / 10 ms). Empty or whitespace-only programs are sent as `pass` (a raw-REPL Ctrl-D on an empty buffer is a soft reset). **Open defect:** chunked exec after a board reset under the session can send Ctrl-D into a friendly REPL (implicit soft reset); it must verify raw mode first.
- `stop` = Ctrl-C x2 50 ms apart then wait for a prompt; at an idle raw prompt it returns `stopped:true` immediately. Latency bound restated: reply within 200 ms when the program is interruptible (the first-written "<100 ms" was met by luck).

### A.3 Errors (section 3)
- Additional `E_PROTOCOL` causes: malformed `socket://`/`rfc2217://` address, unknown `openPolicy`, program source containing bytes `0x03`/`0x04` (after escaping rules), a board answer that violates raw-REPL framing. `E_BOARD_UNRESPONSIVE` also covers an `exec` stage timeout and a serial write timeout. `E_INTERNAL` for `exec` outside raw mode (a bridge bug) and non-OSError exceptions from the serial layer. `E_PORT_BUSY` also when a second Link in the same process opens a held port. On `socket://`, `ECONNREFUSED` maps to `E_NO_DEVICE`. Unplug: the Link raises `E_NO_DEVICE` and invokes a one-shot `on_disconnect` callback which the bridge turns into the `state` event with `reason:"unplugged"`; later calls keep raising until `close()`/`open()`; a deliberately closed link raises `E_NOT_CONNECTED`. (Windows `winerror` outside the small tables currently drops the errno: open defect.)

### A.4 Filesystem ops (section 3) - devfs semantics
- `fs.put` result adds `sent` (bytes sent; 0 when skipped) and `verified` (`"sha256"` or `"size"`); `fs.get` adds `verified`. `expectSha` means "skip only if the board's file has exactly this hash **and** it equals the hash of the local file being sent" (a stale value never skips). Free space is checked first (`statvfs`) and `ENOSPC` raised before writing. Temp name is `remote + ".mpytmp"` (over ~250-byte basenames: `<parent>/~<sha16>.mpytmp`); if the target must be removed first (FAT) and the second rename fails the temp is kept (it holds the only copy). `devfs.clean_orphans(exec_fn, root)` removes stale `.mpytmp` files; the bridge calls it once per session after the first idle sync.
- `fs.manifest` adds `warnings:[{path, errno}]` for unreadable sub-folders; entries may carry `statError:true` (size 0); `exclude` takes absolute device paths or paths relative to `root`; a missing root is `E_FS_ERRNO ENOENT`, a file root `ENOTDIR`. `fs.stat` below a file returns `{exists:false}`.
- `fs.rm`/`fs.rmtree` of a missing path raise `E_FS_ERRNO ENOENT` (not silent success); `fs.rm` of a folder is `EISDIR`; `fs.rmtree` of a file is `ENOTDIR`, `removed` counts files and folders including the root folder, and the bridge requires `confirm:true` at the protocol level. `rmtree` refuses `/`, `""`, `//`, `/.` (`E_PROTOCOL`); **open defect: it must also refuse a top-level mount point such as pyboard `/flash` (or `/sd`) without an additional explicit flag.**
- `fs.mv` never overwrites (`EEXIST`); same-name is a no-op; case-only rename of the same file is allowed; cross-mount is `EXDEV` with a copy-then-delete hint. `fs.mkdir` with `parents:false` is a plain mkdir; `fs.get` creates missing parent folders of `local`.
- Device paths must be absolute with no `.` or `..` segments (`E_PROTOCOL`); `chunk` is 16..8192.
- `identity.profileHints = {modules:[...], frozen: bool, fsTotal, fsFree}`; `caps.paste` is filled by the Link; missing uname/`_build`/`unique_id` are empty strings, never absent keys. `introspect.modules` entries add `kinds`, `consts` and `error`.
- Wire format of device snippets: one `@@<json>` line per record; non-printable-ASCII, quotes and backslashes are transmitted as `key+"x"` hex of the UTF-8 bytes; error records carry the errno number and name.

## Appendix B - clarifications from the fix step (2026-10-12, 646 tests; supersedes A where it differs)

- **Safe-mode host rule is final** (A.1): `urlsplit(url).hostname`; any `@` in the netloc is refused; only `localhost` or a literal loopback IP (`ipaddress.ip_address(host).is_loopback`) is accepted; nothing is resolved. `127.1`, `0x7f.0.0.1`, `127.attacker.example` are refused. The kit (`tools/hwkit/mpy_hwkit.py`) enforces the same variables and is deliberately stricter (dotted-quad 127.x.y.z only); `--simulated` exempts only a non-`serial` serial class or a harness pty. The "open defect" notes in A.1-A.3 about the loopback check, chunked-exec Ctrl-D, and unlisted winerrors are **fixed**.
- **`connect.sync` has a fourth value `"prompt-unverified"`**: the tail looked like `>>> ` but there was no REPL evidence (no banner, and the answer to our nudge was not echo-only). `Link.mode` is `"unknown"`, `sync_evidence` is `""`, nothing is sent. The bridge maps it to state `running` (conservative): file ops answer `E_PROGRAM_RUNNING`, the user is asked before any Ctrl-C. A `"prompt"` verdict implies `sync_evidence` in `raw|banner|echo`. `soft_reset_friendly()` and `hard_reset()` can return it too. Known limit: a program looping on `input('>>> ')` that answers the nudge identically cannot be told apart by bytes alone.
- **Stop (A.2, restated):** `stop` replies at the **first prompt** (about 50 ms plus the board's answer; bound 200 ms when the program is interruptible). The settle period is applied afterwards as a **quiet deadline**: for gap+settle after the last Ctrl-C, ops that write to the board (`exec`, `enter_raw`, `exit_raw`, `sync_to_prompt`, `soft_reset_friendly`) wait first, and a `tty.write` containing Ctrl-C opens a ~90 ms wait. An `exec` that ends with KeyboardInterrupt sets a ~90 ms quiet deadline of its own.
- **`E_CANCELLED` / `E_BOARD_RESET` in exec:** Ctrl-C bytes are counted under the write lock; a submission (chunks plus the terminating Ctrl-D) raises `E_CANCELLED` if the count moved, then the Link re-confirms the raw prompt with Ctrl-A (never a reset) so mode stays `raw` and a cleanup exec can run at once. `E_BOARD_RESET` (nothing sent) when the last prompt seen was friendly or the pending bytes contain a `MicroPython v` banner. An exec whose program is stopped still returns normally with `KeyboardInterrupt` in stderr (devfs maps it to `E_CANCELLED`).
- **`fs.rmtree` gains `allowMount` (default false):** a direct child of `/` that is a mount point (st_dev differs from `/`, a virtual root with empty statvfs, a VFS mount, or the board's working folder) is refused with `E_FS_ERRNO` detail `EPERM`; the error carries `needs_allow_mount` and `mount_reason in {dev, root, vfs, cwd}` so the client can ask again and resend with `allowMount:true`. Nested mounts (`/mnt/sd`) are not covered.
- **Shadow guard is implemented in devfs** (`check_shadow`, parameters `shadow_guard` = module names, `shadow_roots` = absolute import folders, default `['/', '/lib']`; the bridge should pass the absolute entries of `identity.syspath` such as `/flash`, `/flash/lib` on a pyboard) for `fs.put` (remote path), `fs.mv` (destination, skipped when src == dst) and `fs.mkdir`. Refusal happens before any exec: `E_SHADOWS_MODULE`, detail `module=<name>; match=exact|case-insensitive; root=...; path=...`. Case-only variants are refused deliberately (FAT/SD, Windows and macOS hosts cannot tell them apart). `shield.py`, `shield/__init__.py` and `_shield.mpy` all shadow `shield`/`_shield`. **The bridge still has to fill the list** from `config.shadowGuard`, the profile's frozen names and `identity.profileHints.modules`.
- **Upload cancel cleanup:** after an error with a possibly-created temp file, `put_file` tries to remove it twice (2 s each, 0.25 s apart); if it cannot, the error detail ends with `cleanup:"deferred" tmp=<path> (<reason>)` and the exception has `.cleanup == "deferred"` and `.tmp_path`; `clean_orphans()` removes it next session. Cancelling before any snippet was sent makes no round trip.
- **Damaged replies:** a device reply that parses as JSON but has the wrong shape or value is `E_INTERNAL` with detail starting `damaged reply:` everywhere in devfs (`get_file` decodes base64 with validation).
- **Windows names:** `lookup_usb_ids()` and the held-port registry treat `COM` names case-insensitively and accept the `\\.\COM3` spelling; POSIX names stay case-sensitive.
- **Test fixtures:** the unix relay sends SIGINT itself (and swallows that one `0x03`) for the first Ctrl-C while a raw-paste program runs and the pty's ISIG is off, and logs a `sigint` event. On a Windows host the fake board answers ENOENT for device path segments containing backslash, `:` or reserved Windows names.

## Appendix C - behaviour changes from the R1c fix step (2026-10-13; supersedes A/B where it differs)

Reported by the fixers and the reconcile agent after fixing 22 reviewer-reproduced findings; tests: `tests/test_server_fixes.py`, `tests/test_server_pins.py`, `tests/adversarial2/`. Items marked (fixer) come from an individual fixer's report.

- Appendix C / section 3 `disconnect`: while a Run holds the worker, `disconnect` without an explicit `stopFirst` is refused at once with E_PROGRAM_RUNNING (needs_interrupt:true) and the port stays open. `stopFirst:false` closes the port, leaves the program running, and the Run's response is exit:"disconnected". `stopFirst:true` stops the program (Ctrl-C), then closes. This departs from the section 3 row ("programs are not stopped by disconnect unless stopFirst:true"), because an unanswered or silently abandoned Run was the defect. The extension must send stopFirst explicitly during a Run. The default is a one-line change in Server._enqueue.
- Section 6: `disconnect`, `repl.attach` and `repl.detach` are answered immediately even while a Run owns the worker. repl.attach and repl.detach only flip the view flag and never write to the board. Attaching to a connect-time program writes nothing.
- Section 5 state machine: `idle` is only claimed on evidence. From `running`, the pump must see the banner and the prompt and then 0.35 s of quiet. Link.sync_to_prompt must then see a fresh prompt echo after a bare newline (no Ctrl-C, Ctrl-D or reset). A prompt lookalike with no banner before it never gets the newline and stays running. A cancelled Run or an exec that timed out leaves the state `running` (Stop resynchronises with Ctrl-A, never a reset, then goes idle). A board that finishes booting, or a connect-time program that ends by itself, becomes idle on its own.
- Stop: overlapping Stop requests share one Ctrl-C pair and one answer. A Run whose Stop got a prompt but whose end-of-stream never arrives is released after RUN_END_GRACE (3 s) and resynchronised via Ctrl-A, never a reset.
- Link, raw paste: when the board sends its own 0x04 during a raw-paste submission, the Link acknowledges it with Ctrl-D only if no Ctrl-C has been written since the submission began. After a Stop it raises E_CANCELLED and resynchronises with Ctrl-A, never a Ctrl-D on an empty raw buffer (RQ-SAFE-1).
- E_PROGRAM_RUNNING: the hint is student wording ("A program is still running on the board. Press Stop first, or confirm that it may be interrupted."). The machine hint 'repeat with interrupt:true' moved to `detail`. The error carries needs_interrupt:true and sync ("running-program", "silent" or "prompt-unverified"). For sync "silent" the message is "The board did not answer." with a hint to check the port, close Thonny and press reset. The code stays E_PROGRAM_RUNNING and no Ctrl-C is sent before consent.
- tty.write: Ctrl-C always passes (also with run stdin:false and while keystrokes are held). The 4096-byte hold buffer is all-or-nothing: a write that does not fit is refused whole, with order preserved.
- exec: output above EXEC_MAX_BYTES is cut and the response adds `truncated:true` and `outBytes` (the real size). Every response line is guarded at 4 MiB: an over-long response becomes a small error with the same id. An over-long request line keeps its id (salvaged from anywhere in the line, null only if it truly has none).
- Appendix B: the mount refusal of fs.rmtree (and other mount guards) is machine-readable on the wire: error has needs_allow_mount:true and mount_reason ("dev", "root", "vfs" or "cwd"); resending with allowMount succeeds.
- Argument validation order: `local` must be an absolute path (relative gives E_PROTOCOL for fs.put, fs.get and run). Run arguments (for example a control character in the name) are rejected before any interrupt or reset is sent to the board. The CLI resolves a relative `local` against the caller's folder before sending.
- CLI (--script): --port is used for the implicit connect before the first op that needs a board (a script that sends its own connect decides alone). A UTF-8 BOM in the script file is accepted. Output is encoded with replacement, so a non-encodable character never crashes the CLI.
- Process signals: the bridge closes the port cleanly on SIGHUP, SIGTERM and SIGBREAK, and on stdin EOF. It does not stop the program on the board (same as stdin EOF). Windows console-close and logoff events are not handled [U].
- devfs fs.get: the host temp name is `<local>.mpytmp` when basename plus suffix is within 250 UTF-8 bytes (composed and NFD-decomposed). Otherwise it is a hidden `~<sha16>.mpytmp` in the same folder. On Windows the short name is also used when the plain temp path would pass 259 characters. A retry with the short name follows ENAMETOOLONG (winerror 206). An E_LOCAL_IO message names the file the student asked for. A local basename over about 255 bytes now fails at the final replace, after the download.

- Appendix D, connection binding: reset.machine and reset.hard are bound to the connection that existed when the request arrived. If the counter moved while the request waited in the queue (priority 1 ops jump the queue), the request fails with E_CANCELLED ('The board connection changed after the reset was confirmed, so nothing was sent.', hint: check which board is connected now and ask again) and nothing reaches the board. ## Appendix E - sync preconditions and the board clock (2026-10-13, decisions D-21 and D-22)

- `fs.put {ifSha}` is the compare-and-swap that keeps auto-sync from overwriting a board copy that changed since the last sync (a program rewrote it, another PC uploaded, a lab partner's board). The client passes the baseline hash it last synced (or `"absent"` for a file it believes is new). The check and the final rename happen inside one borrowed raw-REPL session and file ops need an idle board, so nothing else can change the file in between.
- New error code `E_DEST_CHANGED` (in `errors.CODES_V11`, like `E_RESET_NOT_OBSERVED`) with the extra `current:{exists,type,size,sha256}` so the client can tell "changed" from "deleted" without another round trip.
- `clock.read` / `clock.set` (decision D-22): the extension sets the board clock from the computer's LOCAL time after a connect when the clock is implausible, only on an idle board. Snippets `clock_read` / `clock_set` are the only ones besides `identity` that touch `machine`, and only `machine.RTC` (pinned by `tests.test_devfs.SnippetAuditTests`).
- `introspect.modules` reports class members (`classes`) for the IntelliSense stubs of custom firmware modules (REPL-based stubs, no firmware source folders).
