### 2026-10-12 - hardware session 1 (instructor present; kit `tools/hwkit/mpy_hwkit.py` 1.0+mpy-upgrade.1, stages A and B; report `tools/hwkit/reports/hwkit-report-20261012-session1.json`, console `tools/hwkit/reports/session1-console.txt`)

Setup: macOS 15.7.8 Intel, Python 3.15 + pyserial 3.5 in a scratch venv, `/dev/cu.usbserial-0001` (CP2102, 10c4:ea60, serial 0001), board running the class firmware. **Motor power was ON; the instructor explicitly accepted that chip resets can spin motor 2 for about 0.3 s** (checklist item 1 waived for this session, recorded in the report via `--motors-on-acknowledged`). To limit resets the matrix was reduced to 3 open policies x 2 cycles plus a baseline (8 opens). The board was reset 4 times by the policies that reset it (V2, V3), so its previous run state was lost.

- **Identity [E]:** `sys.implementation._build == 'WSU_SHIELD'`, `_machine == 'WSU Motor Shield with ESP32'`, MicroPython `(1, 29, 0)`, `_shield.ABI == 1`, `_shield.__version__ == '2930580-dirty'`, `exception_policy() == 2`; root listing `['boot.py', 'test.py']` (no `main.py`); `gc.mem_free()` 164560. Matches the firmware source reading in N-7. The `-dirty` version means the firmware was built from an uncommitted tree (relevant to RQ-COURSE-1 stamping).
- **S-03 (macOS + CP2102, this board) [E, n=2 per policy]:**
  | Open policy | Resets at open | At close/gap | While held open |
  |---|---|---|---|
  | V4: pyserial default open, RTS-then-DTR close (what mpremote 1.29 does on macOS) | **0 / 2** (plus a clean baseline) | 0 / 2 | 0 |
  | V2: DTR and RTS forced low before open, plain close | **2 / 2** (ROM text 13-16 ms after open, `reset_cause` 1) | 0 / 2 | 0 |
  | V3: mpremote's CP210x-on-Windows sequence (low, open, DTR=1 then RTS=1; ordered close) | **2 / 2** (ROM text 15-18 ms after open, `reset_cause` 1) | 0 / 2 | 0 |
  Reading: dropping DTR before RTS while opening passes through the "EN low" state of the CP210x auto-reset circuit and resets the chip; leaving pyserial's default (both asserted) does not. **Consequence for the `Link` (RQ-SAFE-1): on POSIX use pyserial's default open and RTS-then-DTR close (V4); do NOT use mpremote's CP210x sequence there.** That sequence exists for a Windows-only first-open quirk (mpremote `transport_serial.py:70-85`); whether it is right or harmful on Windows is still S-08. A baseline uptime of 15,389,929 ms (4.27 h) with `hook_counts` (19, 5, 5) was unchanged across the V4 cycles, so V4 neither reset nor soft-reset the board.
- **Not yet covered:** Windows (S-08), CH340/S3 boards (U-8), stages C/D/K (Ctrl-C/Stop semantics, soft reset, REPL keys), E (RTS reset), U (unplug), and the bridge itself (S-01 needs R1 code).
- Kit fix from this session: A4 (`motors_ready is False`) is only judged when uptime < 60 s; the board had been running 4.3 h so `True` was expected.
