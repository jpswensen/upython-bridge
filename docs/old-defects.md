## 01-discovery

*Summary:* The user's .venv was never found for two stacked reasons, and the second one hides behind the first. (1) The build they actually installed is the committed 0.3.2 .vsix, which is older than git HEAD. It runs bare `mpremote` through exec and in terminals, never looks for a venv, and ignores mpyWorkbench.pythonPath for every mpremote call. Their hand edit patched only two REPL command strings in the installed dist (one points at ~/src/mpy_remote, which does not exist). Run File and the whole sidebar still use bare `mpremote`. (2) HEAD's resolver is broken by design, and I reproduced this by executing the compiled code against a vscode mock and fixtures. validatePythonPath() tests the global `mpremote` on PATH rather than the candidate interpreter, so a correct .venv python is rejected when no global mpremote exists and a wrong python is accepted when one does. ${workspaceFolder} and relative paths are passed to execFile unexpanded (the user's own settings.json has the literal). Everything falls through silently to 'python3', and that failure is cached globally for 30 s. The "Install mpremote" prompt is dead code, because the Node error 'spawn mpremote ENOENT' never contains 'not found'. Windows is additionally broken in HEAD: POSIX single-quote escaping goes to cmd.exe and PowerShell, and 'py -3' is passed as one filename. This last point is read from the code plus Node's own source, and I could not execute it. Terminal and child_process paths resolve differently (login-shell PATH vs extension-host PATH, three different shells). The fix is a new resolver, not a patch: validate the candidate itself with `python -I -c <probe>`, return a launcher {exe, prefixArgs} with no command strings, spawn with execFile and createTerminal shellPath/shellArgs, cache per folder with single-flight and explicit invalidation, never fall through from an explicit setting, use `python -I -m mpremote`, and ship a one-click venv + pip install with progress UI. A prototype of that probe, layout and classification logic found the real ~/src/mpy_test/.venv (Python 3.13.13, mpremote 1.29.0) in about 110 ms with PATH=/usr/bin:/bin. Full detail, line citations, harness description and the design are in the notes file.

## 02-repl-run

*Summary:* The REPL and Run features are built on the wrong primitive. Every action either types a quoted shell command into a VS Code terminal, or exec()s one in a child process, so up to five independent mpremote processes fight over one exclusive serial port, with no owner, no state, and no error channel. For Run in git HEAD the decisive bug is that mp.fileExists() runs `mpremote fs stat`, which is not an mpremote command; mpremote 1.24-1.29 accept it silently and exit 0. Run therefore always does `exec "import <module>"` against the board's copy of the file: stale code, ImportError when the file was never uploaded (auto-sync is off by default), `if __name__ == "__main__":` skipped, and SyntaxError for file names such as `lab 1.py`. It never runs the editor's code. The REPL terminal is a one-shot `zsh -lc "python -m mpremote connect X"` process. When it exits for any reason (port busy, wrong Python, Ctrl-X, unplug), VS Code disposes the terminal and the stderr is lost. The auto-suspend feature closes the REPL with Ctrl-X and then types a restart command into the already-disposed terminal, so any listing, upload or auto-sync leaves the user without a REPL. A leaked skipIdleOnce flag adds port-lock failures, and a fixed 500 ms sendText Ctrl-C becomes SIGINT if mpremote has not yet entered raw mode (reproduced with a slow login profile). Ctrl-C in the Run terminal does not stop the board program (mpremote sends only Ctrl-B). Stop, Interrupt and Soft reset are `echo -e` hacks that write a literal `-e ` before the control bytes on macOS, so no reset happens. 'Soft reset' with no REPL open is actually a hard machine.reset(). HEAD's POSIX single-quote escaping fails on Windows PowerShell (ParserError) and, per documentation, on cmd.exe. The user ran the older .vsix build (bare `mpremote`, REPL hard-coded to ~/src/mpy_test/.venv); HEAD is different but shares every design flaw. Verdict for this area: rewrite, keep the sidebar layout. The replacement needs one long-lived connection owned by the extension host, a Pseudoterminal as a view onto it, an explicit state machine with timeouts and visible errors, and Run implemented as raw-REPL raw-paste of the editor buffer. Node `serialport` (prebuilds for macOS x64+arm64 and Windows x64/arm64/ia32 verified to exist and load) removes the Python/mpremote dependency, with a pyserial helper as fallback. Notes with the step-by-step failure sequences, experiments and design are in the notes file.

## 03-fs-sync

*Summary:* The old "auto-mirror" is a one-way, save-triggered push (only when the workspace was explicitly "Initialized" and autosync, default off, is enabled) plus Upload-all / Download-all / Clear buttons. It has no comparison, no state read-back, no delete/rename propagation and no conflict handling. The device-FS layer is built on scraping `mpremote fs tree`/`fs ls` text and on mpremote subcommands that do not exist: `fs stat` and `fs mv` are silent exit-0 no-ops in mpremote 1.20-1.29, and `fs mkdir -p` is rejected by argparse. I executed the real compiled old code (including the real `extension.js` activated headlessly) against real mpremote 1.29.0 and a simulated board (unix MicroPython behind a pty<->socket bridge; no serial port touched) and proved: `fileExists()` returns true for a nonexistent path, which is the root cause of "Run current file doesn't work" (it always runs `exec "import module"` against a board copy that autosync never uploaded). The tree parser mislabels extension-less files and all `.mpy` files as folders and drops any name containing "tree". Download-all silently overwrites local edits and aborts midway. Clear Device Files leaves files and misreports counts. Upload-all says "completed" when uploads failed. Every operation is a separate mpremote launch (port open + soft reset): a 7-file/3-folder Upload-all costs 49 launches, one autosave costs 3, and Save-All runs 4 launches concurrently on one port because the mutual-exclusion guard is dead code. HEAD's POSIX single-quote exec string cannot run under Windows cmd.exe. package.json declares 9 Files-view commands with no handler (removed in git fbb4a16) and the Local Files view is undeclared. Recommendation for this area is a rewrite: one long-lived board session speaking JSON, on-device listing/hash snippets (tested), size+sha256 comparison against a recorded base state (3-way), atomic temp+verify+rename writes, preview-first plans, deletes never automatic, backups before destructive actions, and a CI rig using the unix MicroPython port as a fake board. Details, citations, measurements and tested snippets are in the notes file.

## 05-cross-platform

*Summary:* The old extension is unsafe on Windows and partly broken on macOS. The process layer (mpremote.ts, mpremoteCommands.ts, pythonInterpreter.ts: 2,670 of 5,782 lines, holding 29 of the 47 hazards I logged) has to be replaced no matter what. HEAD (7cb90c7) builds every mpremote call and both terminal flows (Run, REPL) as POSIX single-quoted strings. cmd.exe (via child_process.exec) and PowerShell cannot run those, so nothing works on Windows. The shipped VSIX is an older build (bare `mpremote`, double quotes), so HEAD regressed Windows. I reproduced complaint 1 by execution on macOS: the resolver tests a candidate by running the global `mpremote` rather than `<python> -m mpremote`, so it returned the literal `python3` even with a working venv and an explicit `mpyWorkbench.pythonPath`. Run-file fails because `fileExists` uses `mpremote fs stat`, which mpremote 1.26–1.29 accepts but never implements (exit 0, no action), so it always answers "exists". The same contract failure hits `fs mv`, `fs run` and `fs mkdir -p`. Stop and Interrupt write `echo -e '\x03\x03' > <port>` through a shell. `kill()` leaves the real python process holding the COM port on Windows. A backslash regex bug uploads `lib\sensor.py` as a root file named `lib\sensor.py`. From a cross-platform standpoint I recommend a new extension with the same sidebar and layout, reusing the UI shell and a few pure helpers. Its foundation should be argv-only spawning, an absolute interpreter chosen by a unit-tested resolver, a pinned mpremote >= 1.29 (vendored pure-Python wheels, launched hermetically), terminals that run the interpreter directly, tree-kill plus a single port owner, error classification on stable tokens, and a diagnostics command. Nobody can run Windows CI today, so the notes file has a 60-row manual test matrix, an automation tiering, and a GitHub Actions workflow. I executed tested reference helpers (13 node tests), a contract test, a socket-based fake board, and a source guard on macOS. Every Windows claim is read from the code, documented platform behaviour, or inferred; no Windows host was available, and the board was never opened.

## 06-ext-core

*Summary:* The old extension compiles clean under tsc --strict (tsconfig already has strict:true), so its bugs are lifecycle and contract errors rather than type errors. Evidence is a headless harness (fake vscode module plus fake python and mpremote, no serial port touched), reads of VS Code 1.141 source, git history, and a packaging trial. (1) Activation overwrites the user's global mpyWorkbench.connect with "auto" on every start (extension.ts:187), and Run/REPL/Stop/Interrupt refuse "auto". (2) Ten contributed commands have no handler: the whole board-tree context menu except Open, plus refreshPorts; commit fbb4a16 deleted the registrations. (3) pythonInterpreter.validatePythonPath checks a global PATH `mpremote`, not `<python> -m mpremote`, and mis-classifies ENOENT; reproduced by execution, a venv-only mpremote is rejected and even an explicit pythonPath is ignored, falling back to python3. This explains complaint #1. (4) The two serialisation mechanisms are no-ops (markHealthy clears the in-progress flag; withAutoSuspend resets opQueue): three saves ran as three simultaneous mpremote processes. (5) HEAD's POSIX single-quote shellEscape run through exec/cmd.exe will break every board operation on Windows. (6) Run file types into a reused terminal, so a second run behind a while-True program never executes; likely cause of complaint #1's "run did nothing". Also: Refresh is a no-op for 30 s, sync-all reports success despite failures, Board->Local overwrites without confirmation, a view is created that package.json never contributes (error toast every start), untrustedWorkspaces:true while workspace settings can pick the executable, extensionKind/remote cannot see USB (recommend detect-and-disable, not 'ui'), and the repo ships a stale 5 MB .vsix containing a .venv with node_modules and dist committed. About 18% of the 5.5k lines are dead or duplicate. Recommendation: rewrite the core/glue (decomposition and 10 invariants in the notes) and keep the sidebar/command/menu contract as the spec.

## 07-linting-stubs

*Summary:* Complaint 2 is a missing feature, not a bug: the old extension (mpy-workbench 0.3.2) contains no stub, Pylance or Pyright handling at all (grep of src, scripts, package.json finds nothing), so fixing vs rewriting does not change it. "Custom libraries" are four different cases. (a) Files in the locally mirrored lib/: lib/ is not on the import path, so they are unresolved by default; I confirmed this by running pyright. (b) Frozen Python modules: their real .py source is on disk, so evaluating manifest.py gives the source roots. A static JS evaluator matched the firmware's own manifestfile.py on all 99 upstream manifests. (c) C user modules: generate .pyi from the MP_ROM_QSTR tables; the scan found 98.7% of runtime dir() names on 25 core modules and caught a wrong-arity call. (d) .mpy-only libs: need hand-written or introspected stubs. Runtime introspection (micropython-stubber createstubs.py, run for real) loses all signatures: it emits (*args, **kwargs) even for pure-Python frozen code, and pyright then misses a bug that real source or C-scan stubs catch. Use it only for inventory and drift detection. Stock stubs (micropython-esp32-*-stubs, about 135 KB wheels, MIT) must be bundled in the VSIX, because lab networks may block PyPI. The wiring matters: pyright resolves CPython stdlib stubs before extraPaths and site-packages, so putting the stubs in extraPaths or pip-installing them into the .venv leaves time.sleep_ms, ticks_ms, os.ilistdir, sys.print_exception and asyncio.sleep_ms flagged. Fix it with a managed stubPath directory (.mpy-workbench/stubs/active, stock stubs flattened plus the MicroPython stdlib overrides). Pin pythonPlatform to Linux so macOS and Windows machines give identical results. Use pyrightconfig.json with 'extends' rather than .vscode/settings.json. It works for Pylance, Pyright, basedpyright and the CLI, and it is the only place for pythonPlatform. The extension owns a generated, environment-only .mpy-workbench/pyright.generated.json; a user-owned pyrightconfig.json holds typeCheckingMode and rule severities and is created once. MicroPico's settings writer (JSON.parse, then ?? {}, then JSON.stringify) wipes any settings.json that has a comment, and its global ~/.micropico-stubs plus symlink design is fragile. Merge JSONC edits through jsonc-parser, and never edit user arrays. Full design (commands, settings, files, triggers, merge policy, classroom workflows) and test plan are in the notes file, with the complete prototype code inlined.

## 08-mpremote-research

*Summary:* I read mpremote 1.20.0-1.29.0 plus the 1.30.0rc0.post101 pre-release, pyserial 3.5, and MicroPython's pyexec.c and esp32 main.c. I then ran the real mpremote CLI and Python classes against a protocol-level board emulator I built: real unix-port MicroPython behind a bridge that reproduces the raw-REPL framing, served over a pty device node and over socket://. No serial port was opened, and the attached CP2102 board was never touched. The long-form reference, with tables, wire trace, daemon prototype and issue-tracker themes, is in the notes file. Seven things matter most. 1. mpremote has no session across invocations. Every process opens the port, soft-resets the board (up to 1.29), leaves it in the friendly REPL with main.py not running, and closes the port. The 1.30 pre-release turns the soft reset off by default, so state now persists between runs; tooling must say `soft-reset` explicitly. 2. The output contract is the same in every version 1.20-1.30. A MicroPython exception from exec/eval/run goes to stdout with CRLF line endings and `<stdin>` as the file name, stderr is empty, and the exit code is 1. mpremote's own errors go to stderr with exit 1, argparse errors exit 2, and `sys.exit(n)` on the board is swallowed. 3. Unknown `fs` subcommands are silent no-ops with exit 0. The old extension relies on `fs stat`, `fs mv` and `fs run`, which is why fileExists() is always true. That sends Run down an `import <module>` path, so "Run current file" does not run the editor's code, and rename silently does nothing. `mkdir -p` is an argparse error that still opens and closes the port first. Killing or Ctrl-C-ing mpremote does not stop the program on the board; I proved that with a heartbeat file. 4. `mpremote repl` needs a real TTY, so it cannot be hosted on a Pseudoterminal. Port-open failures all collapse into "failed to access ... (it may be in use by another program)". POSIX exclusivity is only an advisory flock. Entering the raw REPL sends Ctrl-C once, so a program that swallows KeyboardInterrupt gives "could not enter raw repl" after 10 s. 5. Opening the port asserts DTR then RTS, which can reset an ESP32 or leave it in ROM download mode. Upstream issue #13504 reports exactly this on macOS with /dev/cu.usbserial-0001 and MicroPython v1.27.0. On this Mac the CP2102 uses Apple's AppleUSBSLCOM driver. Whether this particular board resets on open is unverified; the notes include a protocol to check it. 6. New traps I found by execution. `python -m mpremote` run from a directory containing a student's `serial.py` fails at import. Piped stdout without `-u` puts mpremote's own header lines after the device bytes. A cp1252 stdout makes `fs tree` crash with UnicodeEncodeError. The `fs` helpers have a 10 s silence timeout, while exec/run have no timeout at all. `fs cp -r dir :dir` nests on a repeat run. A board-root file named `os.py` breaks mpremote's own fs helpers (upstream #19475). 7. Recommendation: own the port in one long-lived helper, with its own thin raw-REPL layer on pyserial, rather than spawning mpremote per operation. In-session operations cost 25 ms against 171 ms per process on the emulator, before any real soft reset, and the helper gives a real Stop button, REPL passthrough and one DTR/RTS open per connection. Keep a vendored mpremote 1.29.0 for mip, mount, romfs and as a fallback. If the CLI is used, spawn it with an argv array (never a shell string) as `python -I -X utf8 -u -m mpremote`, with a neutral cwd, a per-port mutex, wall-clock timeouts and process-tree kill. Pin 1.29.0 with a floor of 1.27.0; the old README's >=1.26 is too low.

## 09-architecture-options

*Summary:* Recommend architecture C: one long-lived Python bridge process per VS Code window owns the serial port. The extension is pure TypeScript with no native Node modules. The two talk newline-delimited JSON. The REPL is a Pseudoterminal that only views the bridge's byte stream. The bridge ships inside a single universal VSIX with vendored pure-Python deps and is launched as `python -I -u -X utf8 bridge.py`, so no pip, venv or mpremote install is needed. Scores out of 50: C 45, D (Node serialport) 34, B (hardened stateless) 31, A (old design) 25, E (wrap MicroPico) 21. The call is rewrite the engine and port the shell: reuse the views, commands, menus, decorations, ignore/sync semantics and the whole `contributes` manifest as a spec (roughly 1.2 kLOC of 5.8 kLOC). Replace `mpremote.ts`, the interpreter resolver and most of `extension.ts`. Effort is 7-11 agent rounds, most likely 8-9; the first student-usable build comes after round 4-5. Fixing in place is 5-7 rounds and ends at B. I disagree with note 02, which prefers Node serialport as primary. I choose C because D puts a native binary on the critical path when the instructor cannot test Windows ARM64, and Python is already required for Pylance. The choice stays reversible behind a `Bridge` interface and a one-spike gate. Hardware-free E2E testing is practical. I built a 416-line stdlib TCP fake board that works with real mpremote 1.29.0 and with my bridge. I built a real MicroPython 1.29.0 unix port in about 2 minutes. A WASM MicroPython runs under Node. All of this was executed on macOS Intel only; Windows, Apple Silicon and the real board were not touched.
